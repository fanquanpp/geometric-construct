# 多人联机设计 · NET

> 状态:定稿(2026-09-09 探讨定稿,联网调研同日完成;技术方案与里程碑见 `docs/ROADMAP.md` §2–3);**N0 已实装 + N1 已实装(v0.28.0,`--dualtest` 门禁)+ N2 已实装(v0.29.0,双人入口按设备分流 + 房间流程页 + 事件漏斗;真机双端联测进行中)+ 选图选角编排已实装(v0.37.0,`--roomshot` 六页;真机双端联测进行中)+ N3 骨架预埋未接线**
> 一句话:**三档连接**(同屏双人 → 同网直连 → 异网中继)共用同一套实体与输入槽;
> **主机权威**物理,事件可靠 RPC;**ENet 一贯穿底**,中继服转发全量流量。
> 玩法基线:联机 = **2 人合作闯关**,连接成功后**主机选图 → 双方各认领
> 1–3 位几何体 → 名册位全覆盖开演**(§8,2026-09-13 用户拍板)。

## 0. 决策记录(拍板清单)

| # | 决策 | 理由 |
|---|---|---|
| D1 | 传输 **ENet-only**;WebSocket 只在 `peer_factory` 留签名不实现 | 无 Web 导出计划;ENet 是社区默认答案,两端 API 同构 |
| D2 | 拓扑 = **listen-server 主机权威**,客户端只发输入、收状态 | 权威服务器是教程共识;合作游戏容忍输入延迟 |
| D3 | **不做 lockstep 帧同步** | PC 与 Android 浮点物理不确定,平台跳跃必脱轨 |
| D4 | 中继服**从第一天起转发全量游戏流量**,不做"配对后 P2P 直连" | 蜂窝 CGNAT 打洞成功率低;流量极小(§5)转发成本可忽略 |
| D5 | LAN 发现 = UDP 受限广播 `255.255.255.255` + 手动 IP + 二维码拉起,三重兜底 | 写死子网广播在非 /24 网段失效;手机输 IP 体验差 |
| D6 | 扫码**不做游戏内摄像头**:自定义 scheme intent-filter,系统相机扫码拉起 | 零相机权限、零解码库;二维码自绘 |
| D7 | 版本门禁:发现应答带 `version.gd` 版本 + 官方关卡数据哈希 | 本地联机最高频翻车 = 两端包不一致 |
| D8 | 同步:运动走 20Hz 不可靠通道;事件走可靠 RPC;movers 靠开局时间戳两端推算 | 见 §6;movers 是时间确定性函数,零带宽零漂移 |
| D9 | **首版不做**:主机迁移、客户端预测、WebRTC、第三方后端(Nakama/Photon)、GodotSteam | 逐条理由见 §9 |
| D10 | 三档里程碑(N0–N3)各自独立可发版 | 逐档交付,风险切薄 |

## 1. 三档连接总览

| 档 | 名称 | 通路 | 服务器 | 里程碑 |
|---|---|---|---|---|
| 一 | 同屏双人 | 同设备多输入源 | 无 | N1 |
| 二 | 同网直连 | LAN / 手机热点 / USB 网络共享 | 无 | N2 |
| 三 | 异网中继 | 任意网络,经中继房间服 | 轻量转发服 | N3 |

**不变量**:三档共用同一套 `Player` 实体代码、原生场景装配与 `Main.I`
回调状态机;差别只在 **peer 的创建方式**(`scripts/net/peer_factory.gd`)与
**房间 UI**。档位之间是叠加关系,不是分支关系。

## 2. 公共前置 · 输入槽抽象(N0)

现状 `player.gd` 直接读全局 InputMap(`Input.get_axis` / `is_action_*`)。
重构为**输入槽注入**:

- 接口:`Player.input_source`,方法 `move_axis() / jump_pressed() / jump_held() / sprint()`。
- 四类实现来源:**本地键鼠手柄**(P1 默认 = 现行为,重构后逐像素一致)、
  **第二玩家槽位**(同屏双人)、**触屏**(归 P1,TouchControls 不变)、
  **远端 RPC 注入**(跨设备联机)。
- InputMap 动作加槽位后缀:`p1_move_left / p2_move_left …`;
  默认单人局 = 全部槽位映射到现有动作,零感知。
- 同屏 UI:roster chips 双人高亮(各绑定颜色/描边);暂停归属 = 任一玩家可暂停。

## 3. 第一档 · 同屏双人(同设备)——已实装(v0.28.0)

- **输入映射**:键盘分区(P1 = WASD + Shift / P2 = 方向键 + Ctrl)+
  双手柄各自独占(P1 = 0 号柄左摇杆 / A / 左扳机,P2 = 1 号柄);
  触屏设备首版仅 P1 触屏、P2 手柄(双触屏分区后置,见 §11)。
- **入口**:标题菜单「双人试炼」按钮 → `Main.start_level_dual()`:
  先 `start_level(0)` 正常启动(此刻切换守卫未生效,`_switch_to(0)`
  正常初始化),后翻 `dual_mode = true` 并手动双开前两 Player 的
  `is_active`(双活下 switch_to 已除役)——启序颠倒会吞掉开局操控。
- **双活模型**:各控各的、无切换(chips / Tab / 数字键在双活下除役);
  死亡重生不夺操控(`die()` 不清 `is_active`);到站进门照旧
  (全员到齐 → 终点激活)。
- **镜头**:动态缩放框——`camera_targets()` 双活返回两具绑定体,
  夹住两名玩家 + 最小/最大 zoom 钳制;超距时边缘方向指示
  (HUD EdgeIndicator)。合作解谜**不做分屏红线**。
- **同屏 UI**:roster chips 双人高亮(P1 纸白 / P2 橙描边),数据源 =
  `RosterController.dual_binds()` 的 `[{slot, geo}]` 契约(N2 联机
  绑定集合同形复用);双体芯片恒并示「界 / 边」。
- **关卡**:现有关卡天然兼容(本就是多几何体协作),双人开局固定
  机制试炼场双分位(P1 = roster[0] 疾,P2 = roster[1] 跃);
  单人挑战计时榜可选,不与双人进度混算。
- **玩法**:沿用四几何体分工与承载/配合机制,无新增规则。
- **验证**:`-- --dualtest`(headless 五链路:双活绑定 / 分区输入 /
  双活禁切 / 死亡保操控 / 双体到站);与联机会话互斥
  (NetSession 在局时拒绝进入双活)。

### 4.1 连接三路径(可靠性阶梯)

| 路径 | 拓扑 | 可靠性 | 场景 |
|---|---|---|---|
| A · 家庭 WiFi | 路由器 DHCP,双端同 SSID | 高,但受 AP 隔离制约 | 在家联机,PC 可当主机 |
| B · 手机热点 | 手机开热点、PC 连入,**手机当主机** | **最高** | 推荐默认档;无需外网,出门能玩 |
| C · USB 网络共享 | 手机 USB 共享网络给 PC | 最高,零路由 | 无 WiFi 兜底,顺带充电 |

- B / C 的结构性优势:**主机即网关**。AP 隔离拦的是"客户端↔客户端",
  主机位于 AP/网关位置,客机到主机的通路天然不受影响。
  UI 话术定稿:**"谁当主机,谁开热点"**。
- 默认走 A;发现/直连失败时,诊断文案引导切 B;C 作为无 WiFi 场景手动兜底。

### 4.2 房间发现协议(`lan_beacon`)

- **主机侧**:`PacketPeerUDP` 绑定信标端口(= ENet 端口 + 1)监听
  `DISCOVER` 包,应答 `OFFER`(JSON 字段:协议魔数 `SRNET1` / 房名 /
  版本号 / 关卡数据哈希 / 当前人数 / 上限(首版 2)/ ENet 端口)。
- **客机侧**:向 `255.255.255.255`(受限广播)发 `DISCOVER`,收集应答
  列成"附近房间",带超时自动刷新。用受限广播规避子网掩码坑;
  路由器双频(2.4G/5G 同 SSID)属同一广播域,通常无碍。
- **版本门禁**(D7):版本或哈希不齐 → 房间标灰 + 文案"版本不同,无法加入"。
- **三重兜底**:附近房间列表 → 手动输入 IP:端口(主机界面常驻显示本机 IP)→
  二维码拉起:PC 端把 `speedrouge://join?ip=…&port=…` 画成普通二维码
  (自绘二维码,无需压缩),手机系统相机扫码经
  Android intent-filter 直达房间。
- **连通性预检**:进房前 ping-pong 握手 + 版本核对;失败按症状给诊断文案
  (见 4.3),不出干巴巴的"连接失败"。

### 4.3 系统层坑清单(并入发版检查单)

1. **AP 隔离**:路由器/访客网络/酒店 WiFi 常开客户端隔离——同 WiFi 互不可达。
   症状 = 房间列表为空且手动 IP 超时;文案给路:"建议手机开热点、电脑连入"。
2. **Windows 防火墙**:导出 exe 首次监听 UDP 会弹询问;WiFi 被标"公用网络"时
   默认拦入站。失败文案提示"允许本游戏通过 Windows 防火墙(勾选专用网络)";
   开发期加 `--nettest` 钩子(回环 + 广播收发自测)远程排查用。
3. **Android 权限**:导出预设勾选 `INTERNET` 权限(漏勾是常见翻车)。
4. **主机手机保活**:屏幕常亮(screen keep on)+ 提示加入电池优化白名单;
   息屏/省电会掐断 UDP 监听,表现为"玩着玩着客机全员掉线"。
5. **网段自检**:双端房间页常驻显示各自 IP;`192.168.x` 与 `10.x` /
   `172.16–31.x` 前缀不一致(双路由器组网等)时提前提示"可能不在同一网络,
   试试热点或手动 IP"。

### 4.4 手感

LAN 延迟 1–5 ms,与同屏几乎无差,平台跳跃精度判定完全够用,
**不需要任何延迟补偿**(与 D2/D9 一致)。

## 5. 第三档 · 异网中继

- **拓扑**:建房者即主机,物理与判定的**逻辑权威不变**;中继服是
  dumb pipe,不理解游戏语义——代码极简、永不过时。
- **全量转发**(D4):主机与客机都主动出站连中继,按房号路由包。
  流量账:20Hz × 每包几十字节 × 2 玩家 ≈ 每房间每秒几百字节,
  一台最小 VPS 可扛数百房间——"配对后打洞直连"省下的钱不值得口碑风险。
- **房间标识**:6 位数字房码(中继分配),凭码加入;**首版不做公开房间列表**
  (避开内容审核与匹配复杂度,见 §11)。
- **实现取向**(N3 立项时验证):首选 Godot 无头导出的极简转发服
  (`SceneMultiplayer.server_relay = true`,按房码分组,权威是房间内逻辑指定);
  若需跨游戏版本兼容再降级为 ENet 包级哑管道。房间登记/房码校验走同一进程
  的极简 HTTP 端点,不上 WebSocket(D1)。
- **掉线处理**:`peer_disconnected` 信号驱动——客机掉线:主机提示 +
  该侧几何体处置(见 §11 待议);主机掉线:全员弹回菜单 + 明确提示。
  **主机迁移首版不做**(2 人合作收益低),后期视需求立项。

## 6. 同步规格(三档共用)

> 实装勘误(v0.37.0):本表早期写 `MultiplayerSynchronizer / Spawner`,
> 实装(v0.29.0 起)为**自定义 RPC + 两端装载同一原生关卡场景**——
> 无 Spawner(生成免同步,版本 + 哈希门禁 D7 保证一致)、无 Synchronizer
> (运动快照走自打包 `PackedFloat32Array`)。下表按实装口径记载。

| 类别 | 通道 | 内容 | 频率 |
|---|---|---|---|
| 玩家运动 | 自定义 RPC **不可靠有序**(`rpc_state`) | pos / vel / gravity_dir / facing / 冲刺态 + 关卡时钟 | 20 Hz(`STATE_HZ_DIV=3`),客机速度外推 + 指数靠拢 |
| 客机输入 | 自定义 RPC **不可靠有序**(`rpc_input`) | axis / jump 沿 / jump held / sprint(上传目标槽 = 认领集内当前操控) | 60 Hz(物理帧) |
| 事件(死亡/到站/进门/强化/封印/过关/拉杆/信标) | **可靠** RPC(`rpc_event`) | 走 `Main.I` 既有回调,远端触发同一状态机 | 事件驱动 |
| 移动构件 movers | 开局一次性 | **关卡起始时间戳**(快照携带时钟,客机指数靠拢),两端本地按时间推算 | ≈0(零带宽零漂移) |
| 选图选角 | **可靠** RPC(`rpc_map_picked / rpc_claim / rpc_claims`) | 主机权威仲裁 + 全量广播(v0.37.0,§8) | 事件驱动 |

- **权威与校验**:主机钳制一切输入合法性(位置/速度钳制),防作弊与防崩同源。
- **时钟**:不做全局时钟同步(无预测/无回滚,唯一锚点 = 开局时间戳)。
- **data 层约束**:保持纯数据、可直接序列化(`scripts/net/README.md` 既有约定,
  关卡场景数据与其天然一致(旧 JSON 同构注记,v0.45 前史))。

## 8. 玩法基线(2026-09-13 用户拍板,v0.37.0 实装)

- 联机 = **2 人合作闯关**,沿用现有关卡、承载/配合机制与终点门规则。
- **开局编排 = 选图 → 选角 → 开演**(连接成功后不再直跳固定关):
  1. 主机「开演」→ **MAP 选图页**:从 `LevelData.LEVELS` 注册表选关
     (不同地图提供的几何体阵容不同 = 关卡 `roster` 契约),可靠 RPC
     `rpc_map_picked` 广播定档,两端同进选角页;
  2. **ROLE 选角页**:双方点按认领本关名册位(**每人 1–3 位**,双子一枚
     芯片 = 界/边两具同属);认领经主机权威仲裁(`claim_ok`:不可抢对方
     已持有、不超上限),全量广播 `rpc_claims` 回包驱动两端重建;
  3. **开演条件 = 名册位全覆盖**(`claims_cover`,全员有主,到站契约才可
     满足);主机点亮「开演」,开局绑定 = 认领集,集合内自由切换
     (既有 `cycle_own_slot` / `switch_to_geo` 链路,HUD chips 双方描边)。
- **对半分降级**:未走选图流程的调用点(`--netauto` 等自动化钩子)自动
  退回对半分(`split_roster`,主机前 ⌈n/2⌉ 位)——标准闯关任意关卡
  开合作局与自动化钩子两兼容。
- **修复(v0.37.0)**:`split_roster` 自 v0.22.0 起返回双层嵌套数组,
  `split[1].has(index)` 恒 false → 全部体判给主机、客机绑定集恒空、
  输入上传被三重守卫掐死——即「只有主机能控制角色」的根因;现返回
  平铺双数组并有 `--nettest` 形状断言看守。
- 客机掉线:其认领作废,主机回选图页可再开演(§11 议题 2 维持
  整队弹回房间拍板)。
- **关卡体数多样**属关卡内容产出(机制优先,关卡设计未启动):注册表
  增长后选图页自然出现双几何体 / 多几何体剧目;`levels/pair_trial.json`
  暂不入库(不满足现行 grid_check 规则,修复须经 aseprite 重编译,
  登记待办)。
- **肉鸽 × 联机**仍属深水区(§11 议题 4):肉鸽单人编排已有选角
  (`show_geo_pick`)与选路(章节二选一)环节;多人肉鸽需 per-player
  RunState 与词条归属,待单机词条语言(本轮加成档位)真机验证后立项。

## 9. 明确不做(附理由)

| 项 | 理由 |
|---|---|
| lockstep 帧同步 | D3:跨设备浮点不确定 |
| 客户端预测/回滚 | 合作平台跳跃容忍延迟;后期手感不佳再立项 |
| WebRTC 打洞 | 信令 + TURN 一样要服务器,复杂度更高,且有移动数据吞吐 issue(godot#84645) |
| Nakama / Photon 等后端 | 账号/排行榜/大厅需求出现前是过度设计 |
| GodotSteam | 仅桌面 Steam 分发,安卓商店渠道不可用 |
| 主机迁移(v1) | 2 人合作收益低;文档标注后期视需求 |
